> 评审日期：2026-08-19

> 方法：只读静态审计，5 路并行深挖。**全部数字为 grep / awk / md5sum / 自写 .tres 解析器实测，非估算。**
> 前提转变：**本次按「独立游戏开发导向」判定，不再把「与 Unity 原版逐行对齐」当作架构约束。**

## 0. 结论先行

**有问题，优化空间很大。但问题不是散落的坏味道，而是一个根因长出来的一整片症状。**

根因一句话：

> **这套代码的结构不是为「一个政治模拟游戏」设计的，而是 Unity 原作 C# 代码的转写产物。**
> 原作的数据布局（`data[]` 整型数组）、原作的执行顺序（`TimeScript.cs` 行序）、甚至原作的**移植工单批次**（`外交互动_批1..6`）都被当成了架构。

只要「对齐原版」还是第一约束，这些症状全都是**合理的**——它们是忠实移植的必要代价。
一旦转向独立开发，它们立刻全部变成**纯债务**，而且大部分是可以低风险偿还的债务。

### 四个最重要的判断

**1. 有约 9,000 行代码可以立刻删掉，零行为风险。** 这不是"重构"，是"清理"：

| 项目 | 行数 | 为什么零风险 |
|---|---|---|
| `国家面板.gd` 不可达代码 | **2,174**（占该文件 81%） | 静态可达性已证；函数上自带"[已弃用]""不再走生产路径"注释 |
| `外交互动_补遗.gd` 全文件 | **687** | 19 个动作定义**全部不可达**，逐国链从未引用 |
| 与基类逐字节相同的 helper | **约 5,000**（1,112 份定义） | md5 逐字节验证 |
| `war_system.gd` 样板 | 约 350 | 80 处三行开场 + 71 处成对赋值 |
| 6 份状态栏重复 | 约 690 | 4 个函数 6/6 字节相同 |

**2. 项目反复出现同一种失败模式：建了正确的东西，然后不用它。** 这是最值得警惕的组织性问题，比任何单个技术债都重要：

| 已建好的正确设计 | 实际使用率 |
|---|---|
| `EffectNode` 效果 DSL（22 种类型） | 1,692 个实例中 **90.7% 是 `CUSTOM_SCRIPT` 逃生舱**；8 种类型从未使用 |
| `event_script_base.gd` 全套 helper | 530 个脚本继承了它，却**重抄了 1,112 份逐字节相同的副本**遮蔽掉 |
| `war_action_catalog.gd`（干预数值表） | **0 处调用**，数值在 `can_intervene` 里硬编码了第二份 |
| `资产/数据/修正/*.tres` 的文案字段 | **65/65 名称、60/60 效果文案全部与代码字典冲突，且代码字典优先**——整轨死数据 |
| `GameUIBase`（带节点缓存） | 6 个状态栏**一个都没继承**，各自重写无缓存版本 |
| `EventOption.result_text` 字段 | 1,766 个中 **1,564（89%）是占位符**，真文案搬进了 GDScript 常量 |
| `EventOption.effects` 逐选项数组 | 被创作约定放弃，改成"所有选项指向同一脚本 + 脚本内 `if opt == N`" |
| `cached_diplomacy_scene`（PackedScene 缓存） | 声明了，**0 个消费者**（仍走 `change_scene_to_file`） |

**3. 最该动的不是 `game_manager.gd` 的行数，而是 `数值表[200]`。** 上帝对象是果，平坦整型数组是因。先拆数组，god object 会自己瘦下来。

**4. 动手之前必须先有回归基线。** 128,000 行、执行顺序即游戏规则、**零自动化测试**。现在做任何有语义的重构都是蒙眼拆弹。这一步不能跳。

### 2.3 `war_action_catalog` 为什么被放弃——一个可修的表结构缺陷

`can_intervene:302` 的注释交代了原因：

```gdscript
# 注意 1/4 门槛是 20，但效果扣 30，原版允许负数
match action_id:
    1, 4:
        return d[W.I_AGENTS] >= 20        # ← 表里写 agents:30
```

表只有一个 `agents` 字段，**无法同时表达"检查阈值 20 / 扣除 30"**。于是整张表被丢弃、数值双写在两个 `match` 里。
修法：拆成 `require_agents` / `cost_agents`。**这是一个字段的问题，代价却是一整张表报废。**

### 3.2 `_enable` / `_disable`：562 份副本"一致地偏离基类"

表里最反直觉的一行：与基类逐字节相同 = 0，但**所有副本互相完全一致**。差异只有一处：

```gdscript
# 基类 event_script_base.gd
func _enable(opt: EventOption, text: String) -> void:
	if opt == null:          # ← 562 份副本全部缺失这两行
		return
	opt.text = text
	...
```

典型的"基类事后补加了 null 守卫，既存覆盖版把守卫遮蔽掉了"。

## 4. 问题 C：`数值表[200]` 是数据模型的根因

### 4.1 问题本体

整个玩家国家的状态是一个平坦整型数组：

```gdscript
# world_state.gd:296
@export var 数值表: Array[int] = []
```

- 200 槽，**97 个**有 `I_*` 语义常量，**103 个匿名**；
- **11 个**槽位连名字都放弃了：`"data_41"`、`"data_124"`、`"data_133"`、`"data_170"`…
- 为了字符串查表，维护 `数值索引` 字典：**97 个字段配了 197 个别名**（英文、snake_case 变体、中文各一套）；
- `game_manager.gd` 内对它的写入：**1,165 次**（`+=` 706、`-=` 446、`=` 51），全部经一个叫 `d` 的局部别名；
- 外交层还有 **1,398 处 `d(w, 裸数字)`**。

### 4.2 决定性证据：项目自己已经证明了正确做法

同一仓库里，`CountryData` 用的是**具名字段 + 分组**：

```gdscript
# country_data.gd —— 47 个 @export 字段，带 @export_category
@export_category("国内状态")
@export var 内战中: bool = false       # 原 cw
@export var 政变中: bool = false       # 原 perevorot
```

**全世界 100 多个国家都有干净的具名字段，唯独玩家自己——游戏中被读写最频繁的那份数据——是 200 格整型数组。** 这不是设计选择，是 Unity `GameState.data[]` 的遗留。

### 4.3 症状清单

| 症状 | 证据 |
|---|---|
| 无类型安全 | `d[I_ARMY]` 和 `d[I_BUDGET]` 类型相同，写错下标编译期无感 |
| 约束外置 | `clamp_values()` 在每 tick 末尾统一兜底，而非字段自己保证 |
| **契约可被无声突破** | `外交互动_基础.gd:24-30` 的 `set_d()` **自动 append 扩容**，200 槽契约无处强制 |
| 编辑器不可视 | Inspector 里是一列无名数字 |
| 别名爆炸 | 一字段 2-3 个字符串名，拼错静默失效 |
| **字段语义被劫持** | `外交互动_批3:93/95` 用 `country.内战中` 当"是否已施行金融帮扶"的存储位 |
| 批次约定分裂 | 批1 用 206 处 `W.I_*`；**批2-6 用 1,387 处裸数字，0 处符号常量** |

### 4.4 改法：门面 + 分批搬迁（不推倒）

**第一步**：加具名属性，内部仍读写数组。零破坏。

```gdscript
# world_state.gd —— 新增，旧代码完全不受影响
var 军力: int:
    get: return 数值表[I_ARMY]
    set(v): 数值表[I_ARMY] = clampi(v, 0, 1000)

var 预算: int:
    get: return 数值表[I_BUDGET]
    set(v): 数值表[I_BUDGET] = v
```

好处立刻显现：
- 新代码写 `ws.军力 -= 100`，与 `d[W.I_ARMY] -= 100` 不是一个可读性量级；
- **钳制回归字段自身**，`clamp_values()` 可逐项退休；
- 编辑器/调试器能看到名字；
- 拼写错误从运行时静默失效变成**编译期错误**。

**第二步**：按域分组进子资源（经济/政治/外交/军事）。
**第三步**：新代码只准用具名属性；老代码改到哪清到哪。
**第四步**：`数值表` 降级为存档兼容字段，最后删除。

### 6.3 关键洞察：阻塞点不是表达力，是三个机制缺口

| 4. 算术与集合运算 | ~115 个脚本 | 真实缺口 |

### 6.5 `trigger_priority`：三套量纲，已产生真实碰撞

`trigger_priority` 是**全局排序键，即业务语义**（同 tick 只触发排序最前的满足者）。它有 3 套并存量纲：

| 约定 | 事件数 |
|---|---|
| `编号 × 100` | 482 |
| `编号 × 10` | 55 |
| 小序数（64, 65, 71, 182…，**排在几乎所有 ×100 之前**） | 11 |
| 缺省 `-1`（回退 `扫描序 × 10`） | 31 |

**已实测的真实碰撞：**

```
priority = 2400 : event_024_post_mao_course (24×100) ⟷ event_240_cultural_revolution_verdict (240×10)
priority = 10000: event_100_government_crisis (100×100) ⟷ event_1000_advisors (1000×10)
```

并列时靠 `event_id` 字典序**任意决胜**。这是把"顺序"编码进"编号 × 魔法系数"必然产生的碰撞。

**改法**：删掉数值语义，改为**显式有序清单**（一行一个 `event_id`）。顺序即业务规则，就该写成人类可读的顺序。

### 6.7 `.tres` 是合适的格式吗

**是，但用错了。不建议整体换格式。**

44% 的噪声主要来自**创作约定**（每选项一个重复 `CUSTOM_SCRIPT`、220 个多余声明、89% 占位符），不是格式本身。

| 方案 | 可 diff | 批量编辑 | 类型安全 | 引擎集成 | 长文案 |
|---|---|---|---|---|---|
| 现状 `.tres` + GDScript 双轨 | 差 | 不可 | 强（枚举整数锁死） | 原生 | 差（89% 占位符） |
| 单一大 JSON | 中 | 可 | 无 | 需加载层 | 中 |
| CSV / 电子表格 | 好 | 极好 | 无 | 需导入器 | **不适用**（单条文案常超 500 字） |
| **推荐：`.tres` 收窄 + 文案外置** | 好 | 好 | 强 | 原生 | 好 |

`.tres` 唯一不可替代的优势：`uid://` 真引用（重命名资源自动更新）+ Inspector 类型检查。

**但有一个格式代价必须记账**：`expr_node.gd` 的注释——

```gdscript
# 新类型必须追加在组合节点之后，不能插入前方：旧 .tres 按枚举整数序列化。
```

数据文件里存的是 `type = 25` 而不是 `COUNTRY_FIELD_EQUALS`。**枚举顺序成了存档格式**，只能追加不能重排。这是 `event_factory.gd` 敢于"冻结 DSL"的技术原因。**改法：`.tres` 里存字符串键，不存枚举整数。**

### 6.8 `decision_atoms.gd`（1,786 行）：不要为消行数动它

- 205 个 `static func`，185 个公开原子，**184 个被调用**（99.5% 使用率）——不是死代码，不是 God Object；
- 53 个原子塌缩成 **6 个骨架**（`v = d[IDX]; return v CMP N if yes else ...`）；
- **121 个原子带 `yes: bool` 翻转参数**——`is_traditional(false)` 在调用处完全不可读，而 GDScript 有 `not`；
- 每个函数带原版文件/行号注释，**对复刻目标这个 1:1 结构是资产**：审计成本 O(1)。

**真正的问题不在内部重复，而在系统级冗余**：决议条件用 Callable 原子，事件条件用 `ExprNode` 树，**两套系统表达同一批谓词**（`has_agents` vs `RESOURCE_AT_LEAST("agents")`、`_mod_active` vs `MODIFIER_ACTIVE`、`_event_done` vs `PREV_EVENT_DONE`）。这是内容层最大的架构冗余。

**建议**：让决议条件改用 `ExprNode`，`decision_atoms` 收缩为"`ExprNode` 无法表达的复合谓词"。**不要**用表驱动重写它——会把"对着原版逐条核对"从 O(1) 变成 O(n)。

### 7.5 逐国链：4 个槽位，863 次无条件覆写，零冲突检测


四个全隐式的性质：

3. **两个全局否决在最后**——块J 直接 `return []`，块K 丢弃全部槽只留"发展贸易"。
4. **第二道截断**——`国家面板.gd:2662` 又 `resize(4)`，两处不同的容量假设。

`_main_chain` 是**单函数 1,913 行**，其中第 25 个分支 `elif n != 29:` 是一个**跨 1,461 行的兜底块**，内嵌 97 个 `n ==` 测试。要找 `n == 137` 得手动翻 1,461 行。

**加一个国家按钮**要先答对四个问题：写在哪、用哪个槽、会不会被尾部块覆盖、caption 空格怎么排。**31 个动作编号已存在 caption 拼写漂移**：

```

```

**改法**：改成"规则表 + 小解释器"，用 4 条派生规则消掉 384 次（44.5%）`_show`：

```
规则「发展贸易」: …                                          → 替掉  89 处
规则「军事同盟」: …                                          → 替掉  64 处
```

并让解释器在 debug 构建里对**槽位冲突 `push_warning`**——这是当前 863 次覆写完全缺失的保护。

### 7.6 `war_system.gd`：薄框架 + 超厚数据表

5,232 行 / 145 个全 `static func`：

|---|---|---|
| **83 个逐场战争结局脚本** | **3,686** | **70.4%** |

两个具体问题：

- `apply_war_result` 359 行 = **72 个 `if war_id == N:`** 手写跳转表，每个分支是同一段四行模板；

- **18 个函数超过 100 行**，最大 `_fortnight_modifiers` = **666 行**（内含 41 个 `if _mod_active(w, N)` 复制块）；
- `tick()` 是 29 个调用的硬编码序列，注释明写"原版日块行序"。

### 关键认识：拆分顺序反了

直觉是"先把 7,528 行拆开"。**不建议先做**：`tick()` 里那 29 个调用的**顺序本身就是游戏规则**。在没有基线时拆分文件，唯一要保证的就是"顺序没变"，而这恰恰是搬家时最容易错的。

**正确顺序**：基线 → 删纯重复 → 拆 `数值表` → **最后**拆文件。
拆 `数值表` 后再拆文件会容易得多：函数签名从 `(d: Array[int], w: WorldState)` 变成 `(w: WorldState)`，到处传的裸数组别名 `d` 消失，模块边界自然浮现。

### 目标形态

```gdscript
func tick() -> void:
    if world == null or current_event_id != "": return
    var 上月 := world.date.month
    var 上年 := world.date.year
    world.date.advance()

    每日结算.执行(world)
    if world.date.year != 上年:  每年结算.执行(world)
    if world.date.month != 上月: 每月结算.执行(world)
    if world.date.day % 7 == 0:  每周结算.执行(world)
    if world.date.day % 14 == 0 and current_event_id == "":
        双周结算.执行(world)

    战争系统.检查结束(world)
    EventEngine.check_and_fire()
    成就系统.周期检查(world)
    date_changed.emit(world.date)
    stats_changed.emit()
    _check_autosave()
```

**重要**：`双周结算.执行()` 内部那 35 个步骤的顺序，应写成一张**带编号的显式步骤表**，并注明「**这是本作的结算顺序**」——而不是「原版 TimeScript 的行序」。顺序从此是你们自己的设计资产。

## 9. 问题 H：工程健康

### 9.1 零自动化测试（最高优先级）

- 全项目**没有任何测试**；
- 128,000 行、**执行顺序即游戏规则**、4 个 autoload、13 处 `static var` 缓存；
- 现有流程是"改完在编辑器里人工点一局"。

**这是所有重构建议的前置阻塞项。**

**最小可行基线（不需要测试框架，编辑器内跑即可，约 100 行）**：

1. 固定种子 + 固定开局（`rng_seed` 写死）；
2. 空推进 N 个双周（如 3 年 = 78 个双周），不触发任何玩家操作；
3. 每个双周结束时把 `数值表` 全量 + 关键国家字段 + `empires[]` 序列化成一行 JSON；
4. 存成 `测试/基线_3年.json`；
5. 重构后重跑，逐行 diff。**一个字节都不能变。**

配套：把 13 处 `static var` 缓存注册到统一的 `重置全部()`，保证同进程跑第二局不串味——这是基线可重复的前提。

**投入产出比高于本报告其它任何一条。**

### 9.2 存档格式脆弱

```gdscript
var err := ResourceSaver.save(world, path)    # 直接序列化整个 WorldState
```

读档端是一串手工补丁：

```gdscript
if world.数值表.size() < 200: world.数值表.resize(200)
world.techs.ensure_size()
_migrate_legacy_map_owner_overrides()
WAR_SYS.migrate_legacy_war_timeouts(world)
_migrate_legacy_global_flags()
```

- **没有 `save_version`**，只能靠"size 不够就补"嗅探；
- 直接序列化 `Resource` 意味着**任何 `class_name` 或字段改名都破坏旧档**——与"要重构"直接冲突；
- `.res` 内嵌 `class_name` 逼出了 hack：`ResourceLoader.load(path, "", CACHE_MODE_IGNORE)`（不敢传 type_hint）；
- `ExprNode` 枚举整数也进了资源，进一步锁死重构自由度。

**改法**（必须在动 `数值表` 之前）：
1. 加 `save_version` + 集中式 `存档迁移.gd`；
2. 中期改**显式字典存档**（`to_dict()`/`from_dict()` + JSON），把存档格式与运行时类结构解耦；
3. 存字符串键，不存枚举整数。

### 9.3 性能：四个具体问题

| # | 问题 | 实测 | 改法 |
|---|---|---|---|
| 1 | **每 tick 为 73 个事件 `new()` 一个对象** | `event_engine.gd:433` `trigger_script.new()` + `has_method()` 反射，全部立刻丢弃 | 缓存实例或改 `static func`。**5 行改动** |
| 2 | 每 tick 全量扫 583 个事件 | 命中即返回，但**多数日子没有事件触发**，扫完是常态 | 按日期窗口分桶；已完成的 `fire_only_once` 物理移除；便宜条件前置短路 |
| 3 | **状态栏每 tick 40 次递归 `find_child`** | `date_changed` + `stats_changed` 连发 → 2 次 `_refresh` × 20 次 `find_child(name, true, false)`；`外交.tscn` 有 167 节点 | 状态栏 `extends GameUIBase`（**已有节点缓存，但 6 个状态栏一个都没继承**） |
| 4 | `概览.gd` 每 tick 销毁重建修正列表 | `remove_child` + **`.free()`（同帧立即释放）** + `instantiate()`，条目数量级百位 | 对象池，或只在内容真变时重建 |

另外 `科研.gd` 用 `_process` 每 10 帧全量重建 169 节点界面（6 FPS 刷新率），而 `GameManager` **已有 `tech_completed` 信号**却没用。

### 9.4 Android 适配：布局与目标平台冲突

| 指标 | 实测 |
|---|---|
| `offset_*` 硬编码行 / 节点数 | **3,684 / 1,090 = 3.38**（≈每节点写满 4 个 offset） |
| `*Container` 节点 | **13（1.19%）** |
| `layout_mode = 0`（绝对定位） | 543 |
| 4 个最大 2D 界面（科研 169 / 派系 147 / 经济 126 / 政治 74 节点）的容器数 | **全为 0** |

规律：**节点越多的界面，容器用得越少。** 反例是 `主菜单.tscn`（20 节点）——全项目唯一容器化良好的场景。

冲突点：`project.godot` 设了 `stretch/aspect="expand"`。`canvas_items` 模式救了硬编码坐标（等比例分辨率下视觉正确），但 `expand` 表示**宽高比变化时扩展可见区域**。Android 实际 19.5:9 / 20:9 会把 viewport 横向扩到约 2340×1080 逻辑像素，此时：

- `anchors_preset = 15` 的背景跟着拉宽（正确）；
- 但所有 `offset_right = 1875` 之类的元素**仍钉在 x=1875**，右边凭空多出约 420 逻辑像素空白，UI 整体偏左堆积；
- **3,684 行硬编码 offset 没有一处能自适应。**

且 `场景/` 下 **0 处** `OS.get_name()` / `OS.has_feature()` 分支——输入做了触屏适配（`世界地图渲染.gd`、`轨道摄像机.gd`），**布局完全没做**。

**最小改动**：`aspect` 改 `keep`（加黑边，硬编码坐标立即全部正确）。`expand` 则要求容器化 4 个大界面，工作量在千行 `.tscn` 量级。

## 12. 明确不要做的事

1. **不要重写。** 128,000 行里有巨量真实的游戏设计信息（数值、分支、741,755 字文案）。重写会丢掉它，而且没有基线你甚至无法知道丢了什么。全部建议都是原地改造。
2. **不要先拆 `game_manager.gd` 的行数。** 那是最显眼的问题，但收益依赖 `数值表` 已具名化。顺序反了会做两遍。
3. **不要在没有基线的情况下动任何结算顺序。** 顺序即平衡。
4. **不要整体迁移内容格式到 JSON/CSV/自定义格式。** `.tres` 44% 的噪声主要来自**创作约定**，不是格式。CSV 尤其不适用——内容主体是 741,755 字叙事散文，单条平均 133 字。先按阶段 4 收窄，再评估是否还需换格式（大概率不需要）。
5. **不要为消行数重写 `decision_atoms.gd`。** 它的 1:1 转写结构（含原版行号）是审计资产，用表驱动换回几百行会让"对着原版逐条核对"从 O(1) 变成 O(n)。它的真问题是与 `ExprNode` 的系统级重复。
6. **不要盲删 `_leave_alliances` 的 57 份副本。** 5 套 tag 列表是真实语义分叉，必须对原版逐项裁决。
7. **不要删掉 846 条 `.cs:行号` 出处注释。** 它们的价值从"规格"变成了"这个数值的来历"，对调平衡仍有用。只是不再让它们决定代码结构。
8. **不要一次性重命名全项目。** 改名与逻辑重构分开提交，否则 diff 无法审阅。
9. **不要默认删 `外交互动_补遗.gd`。** 19 个不可达动作可能是**功能缺失**（关系正常化、解放军增援、推翻波尔布特等），应先判断该接线还是该删。

### 如果只能做三件事

**① 阶段 0 的基线工具** → **② 阶段 1 的纯删除（−9,000 行，零风险）** → **③ `数值表` 具名化**

做完这三件，其余每一项的修复难度都会下降一个档次。

### 最后一句

这个项目的**代码质量并不差**——节点命名、路径健壮性、shader 层、`ResScan` 导出兼容层、`CountryData` 的字段设计、`WarDef` 的数据化管道，都做得比同类项目好。

它的问题是**单一的、结构性的、且有明确根因的**：架构继承了 Unity 原作的数据布局与控制流，而团队用"先对齐原版"的排序把结构优化无限期推后了。

**转向独立游戏开发导向，最大的意义不是换个技术方案，而是让"结构优化"第一次获得动手许可。**
